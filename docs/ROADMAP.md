# 개인 개발 블로그 (Notion CMS) 개발 로드맵

Notion을 CMS로 활용해 별도 배포 과정 없이 글이 자동으로 반영되는 개인 기술 블로그를 구축한다.

## 개요

본 프로젝트는 Notion 데이터베이스를 CMS로 사용하여 다음 기능을 제공하는 개인 기술 블로그다:

- **글 목록/상세 조회**: Notion에 작성한 글을 홈과 상세 페이지에서 확인
- **카테고리 필터링**: Category 속성 기준으로 글을 분류하여 조회
- **검색 기능**: 제목/태그 기준으로 글 검색
- **반응형 디자인**: 모바일/태블릿/데스크톱 대응

## 개발 순서 및 근거

**구조 우선 접근법(Structure-First Approach)** 을 따른다. 즉 실제 기능(Notion 연동)보다 애플리케이션의 골격을 먼저 완성한다.

1. **프로젝트 초기 설정 (골격 구축)** — 라우트/타입/환경 변수 등 다른 모든 작업이 의존하는 기반을 먼저 만든다. 이게 없으면 이후 작업이 서로의 완성을 기다려야 한다.
2. **공통 모듈/컴포넌트 개발** — 더미 데이터로 UI를 완성해 페이지 간 재사용 컴포넌트를 한 번만 만든다. Notion API 연동 전에 UI가 확정되므로 API 개발과 병렬 진행이 가능하다.
3. **핵심 기능 개발** — 더미 데이터를 실제 Notion API 호출로 교체한다. UI가 이미 완성되어 있어 데이터 배선(data wiring)에만 집중할 수 있다.
4. **추가 기능 개발** — MVP 이후 우선순위가 낮은 기능(검색 고도화, UX 개선)을 핵심 플로우가 안정된 뒤에 추가한다.
5. **최적화 및 배포** — 기능이 모두 완성된 뒤에 성능/캐싱/배포를 다뤄야 불필요한 재작업을 피할 수 있다.

각 단계가 끝나면 완료 기준을 충족했는지 확인한 뒤 다음 단계로 넘어간다.

## Phase 1: 프로젝트 초기 설정 (골격 구축)

**왜 이 순서인가**: 라우트 구조, 타입, 환경 변수, Notion 데이터베이스는 다른 모든 작업의 전제 조건이다. 여기서 확정해두면 UI 개발과 API 개발이 서로 기다리지 않고 병렬로 진행될 수 있다.

**예상 소요 시간**: 2~3일

- **Task 001: 라우팅 및 페이지 골격 구성** ✅ - 완료
  - Next.js App Router 기준 라우트 생성: `/`(홈), `/posts/[slug]`(글 상세), `/category/[category]`(카테고리)
  - 각 페이지의 빈 껍데기(placeholder) 컴포넌트 생성
  - 공통 레이아웃(`app/layout.tsx`)에 헤더/푸터 골격 구현
  - 완료 기준: 3개 라우트 모두 접속 가능하고 페이지 간 이동이 정상 동작

- **Task 002: 타입 정의 및 환경 설정**
  - `@notionhq/client` 패키지 설치
  - `.env.local`에 `NOTION_API_KEY`, `NOTION_DATABASE_ID` 등 환경 변수 설정
  - `Post`, `Category`, `Tag` 등 TypeScript 타입/인터페이스 정의 (`lib/types.ts`)
  - Notion 데이터베이스 필드(Title/Category/Tags/Published/Status/Content) → 타입 매핑 문서화
  - 완료 기준: 타입 파일이 존재하고 `tsc`/`eslint`가 에러 없이 통과

- **Task 003: Notion 데이터베이스 준비**
  - Notion 워크스페이스에 데이터베이스 생성 (PRD 5번 구조에 맞춰 Title/Category/Tags/Published/Status/Content)
  - Integration 생성 및 API 키 발급, 데이터베이스에 Integration 공유 설정
  - 샘플 글 2~3개 입력 (Status: 발행됨/초안 혼합)
  - 완료 기준: Notion API로 데이터베이스 조회 스크립트 실행 시 정상 응답 수신

## Phase 2: 공통 모듈/컴포넌트 개발 (더미 데이터 활용)

**왜 이 순서인가**: Notion API 연동 전에 더미 데이터로 UI를 완성하면 컴포넌트를 한 번만 만들고 재사용할 수 있고, 실제 데이터 연동 시점에는 UI 변경 없이 데이터만 교체하면 된다.

**예상 소요 시간**: 3~4일

- **Task 004: 공통 UI 컴포넌트 라이브러리 구축**
  - shadcn/ui 기반 컴포넌트 설치 (Card, Badge, Button, Input 등)
  - `PostCard`, `CategoryBadge`, `TagList`, `Header`, `Footer`, `SearchBar` 컴포넌트 구현
  - Tailwind CSS 기반 디자인 시스템/스타일 가이드 정리
  - 완료 기준: `/demo` 페이지에서 각 컴포넌트가 정상 렌더링됨

- **Task 005: 더미 데이터 및 유틸리티 함수**
  - 실제 Notion 응답 형태를 모사한 더미 `Post` 데이터셋 작성
  - 날짜 포맷팅, slug 생성, 카테고리/태그 필터링 유틸 함수 작성
  - 완료 기준: 유틸 함수가 예상 입출력대로 동작함을 확인

- **Task 006: 전체 페이지 UI 완성 (더미 데이터 사용)**
  - 홈(`/`): 글 목록, 카테고리 필터 UI, 검색 입력 UI
  - 글 상세(`/posts/[slug]`): 본문 레이아웃, 메타정보(카테고리/태그/발행일) 표시
  - 카테고리(`/category/[category]`): 필터링된 글 목록 UI
  - 모바일/태블릿/데스크톱 반응형 레이아웃 적용
  - 완료 기준: 3개 페이지 모두 더미 데이터로 완성되고 주요 breakpoint에서 레이아웃 깨짐 없음

## Phase 3: 핵심 기능 개발 (실제 Notion 연동)

**왜 이 순서인가**: UI가 이미 완성되어 있으므로 이 단계는 순수하게 더미 데이터를 실제 API 호출로 교체하는 데 집중할 수 있다. API 연동과 비즈니스 로직에는 Playwright MCP를 통한 테스트가 필수다.

**예상 소요 시간**: 4~5일

- **Task 007: Notion API 연동 - 글 목록 조회** - 우선순위
  - `lib/notion.ts`에 Notion 클라이언트 초기화
  - `Status = 발행됨` 필터 + 최신순 정렬 쿼리 구현
  - 홈 페이지 더미 데이터를 실제 API 호출로 교체
  - Playwright MCP로 홈 페이지 글 목록 렌더링 E2E 테스트
  - 완료 기준: 실제 Notion 글 목록이 홈에 표시되고 초안(Status≠발행됨) 글은 노출되지 않음

- **Task 008: Notion 글 상세 렌더링**
  - slug 기준 단일 글 조회 API 구현
  - Notion 블록 콘텐츠를 블로그 포스트 형태로 렌더링
  - 존재하지 않는 slug 접근 시 404 처리
  - Playwright MCP로 글 상세 페이지 E2E 테스트 (본문/이미지/코드블록 렌더링 확인)
  - 완료 기준: 실제 Notion 글 상세가 정상 렌더링되고 잘못된 slug는 404 처리됨

- **Task 009: 카테고리 필터링 연동**
  - Category 속성 기준 서버사이드 필터 쿼리 구현
  - `/category/[category]` 페이지 실제 데이터 연동
  - Playwright MCP로 카테고리 필터 E2E 테스트
  - 완료 기준: 카테고리 선택 시 해당 카테고리 글만 정확히 표시됨

- **Task 009-1: 핵심 기능 통합 테스트**
  - Playwright MCP로 홈 → 상세 → 카테고리 전체 사용자 플로우 테스트
  - Notion API 오류/빈 데이터/네트워크 실패 등 에러 핸들링 검증
  - 완료 기준: 주요 플로우에 대한 E2E 테스트가 모두 통과

## Phase 4: 추가 기능 개발

**왜 이 순서인가**: PRD 상 MVP 범위에서 검색과 고급 필터는 최소 기능으로만 제공하도록 명시되어 있다. 핵심 조회/상세 플로우가 안정된 뒤에 추가하는 것이 재작업 위험을 줄인다.

**예상 소요 시간**: 3~4일

- **Task 010: 검색 기능 구현**
  - 제목/태그 기준 검색 구현
  - 검색 결과 없음 상태 UI 처리
  - Playwright MCP로 검색 플로우 E2E 테스트
  - 완료 기준: 검색어 입력 시 제목/태그 기준으로 정확한 결과가 반환됨

- **Task 011: UX 개선 및 부가 기능**
  - 글 목록 페이지네이션(또는 무한 스크롤) 적용
  - 글 상세 목차(TOC), 코드 블록 하이라이팅 등 가독성 개선
  - 완료 기준: 목록/상세 페이지에서 UX 개선 사항이 정상 동작함

## Phase 5: 최적화 및 배포

**왜 이 순서인가**: 기능이 모두 완성된 뒤에 성능 측정과 캐싱 전략을 적용해야 최적화 작업이 이후 기능 변경으로 무효화되지 않는다. 배포는 최종 단계에서 한 번에 확정한다.

**예상 소요 시간**: 2~3일

- **Task 012: 성능 최적화**
  - ISR(Incremental Static Regeneration) 또는 캐싱 전략 적용으로 Notion API 호출 최소화
  - `next/image` 기반 이미지 최적화, 폰트 최적화
  - Lighthouse 성능 점수 측정 및 개선
  - 완료 기준: Lighthouse 성능 점수 90점 이상 달성

- **Task 013: 배포 파이프라인 구축**
  - Vercel 프로젝트 연결 및 환경 변수(NOTION_API_KEY 등) 설정
  - 빌드/lint 체크 기반 CI 구성
  - 프로덕션 배포 및 최종 E2E 스모크 테스트
  - 완료 기준: 프로덕션 URL에서 홈/상세/카테고리 플로우가 정상 동작

## 진행 상태 표기 규칙

- Phase 제목 옆 `✅`: 해당 Phase의 모든 Task 완료
- Task 옆 `✅ - 완료`: 완료된 작업 (완료 시 `See: /tasks/XXX-xxx.md` 참조 추가)
- Task 옆 `- 우선순위`: 즉시 착수해야 할 작업
- Task 옆 상태 없음: 대기 중인 작업
